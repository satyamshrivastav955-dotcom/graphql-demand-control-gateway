# Evaluation methodology and results

Everything here is regenerated by one command from the repository root:

```bash
pip install -r ml/requirements.txt
python -m ml.run --seed 42          # dataset -> model selection -> held-out evaluation -> ml/reports/*
```

Outputs: `ml/reports/evaluation.json` (served to the dashboard), `evaluation.md` (full tables), `dataset.json`,
`pr_curves.png`, `per_category.png`, and the model artifact `backend/core/models/risk_model.{joblib,json}`.
The full tables are in [`ml/reports/evaluation.md`](../ml/reports/evaluation.md); this page explains the method and
summarises what the results do and do not show.

## Question

Does adding a trained classifier to a transparent rule scorer detect operation-level GraphQL abuse better than the
simple controls most gateways ship with, without flooding operators with false positives, and does that hold for
abuse patterns the classifier has not seen?

## Method

* **Data** ([dataset card](../ml/DATASET_CARD.md)): synthetic operations from a fictional schema, 12 benign and
  11 abusive categories with overlapping parameter ranges, de-duplicated at the skeleton level, split 60/20/20 by
  category. Seed, sizes and per-category counts are recorded in the report.
* **Methods compared** (all on the same held-out test split):
  1. *Hard limits only* - the gateway's limits with no scoring.
  2. *Depth/cost threshold* - one depth and one cost threshold tuned on the validation split.
  3. *Rule scorer* - rules + hard limits, no ML.
  4. *ML classifier* - the shipped model alone (p ≥ 0.5).
  5. *Combined (production)* - rules blended with the model + hard limits, i.e. the code path the gateway runs.
     The report verifies the vectorised evaluation against `GraphQLGateway.evaluate` on sampled operations.
* **Detection** means *flagged*: at least MEDIUM_RISK (alert or enforcement) or a hard-limit violation. The
  stricter "enforced" (decision ≠ ALLOW) recall/FPR are reported next to it.
* **Model and weight selection** use the validation split only, by *pooled leave-one-attack-category-out* F1:
  the model is retrained without one abusive category and must catch that category. Inference latency breaks ties.
* **Generalisation**: the same leave-one-category-out procedure on the test split, per category.
* **Real queries**: 208 de-duplicated real GraphQL queries (NL2GQL test set) measure false positives.
* **Confirmation set**: an independently generated dataset (different seed) scored once, with operations that
  share a skeleton with the training data removed.
* **Overhead**: offline analysis+scoring latency per method, and end-to-end gateway latency through the ASGI app with
  a stub upstream and an SQLite write per request.

## Results (seed 42; see the report for every number)

| Method | Precision | Recall | F1 | FPR |
|---|---|---|---|---|
| Hard limits only | 0.76 | 0.39 | 0.51 | 0.11 |
| Depth/cost threshold (tuned) | 0.52 | 0.95 | 0.67 | 0.77 |
| Rule scorer | 0.68 | 0.90 | 0.77 | 0.38 |
| ML classifier | 1.00 | 1.00 | 1.00 | 0.00 |
| Combined (production) | 0.79 | 0.99 | 0.88 | 0.24 |

What this shows, and what it does not:

* **The combined scorer clearly beats the limits-only and single-threshold baselines** (F1 0.88 vs 0.51 / 0.67),
  and keeps a 3.4% false-positive rate on real benign queries (0% for the rules and hard limits alone).
* **The classifier's near-perfect in-distribution score is not evidence of a good detector.** Alone it scores
  F1 ≈ 1.00 on the held-out split, yet when a whole abusive category is withheld from training its recall collapses
  (e.g. 0.00 for `field_duplication` and `wide_selection`, 0.19 for `introspection`), while the rules keep 0.74-1.00.
  It has learned the generator's structural signatures. That is why the production score is a blend whose weight is
  chosen on withheld categories rather than on in-distribution F1, and why the rules always retain the final say
  for very high rule scores.
* **False positives on the synthetic benign class are a stress number** (24% flagged, 19% enforced): the class
  deliberately contains heavy hard negatives (14-widget dashboards, wide reports, depth-9 views). On real queries
  the rate is 3.4%.
* **Nothing here predicts accuracy on production traffic.** One fictional schema, one author, labels from
  generator intent. Behavioural signals and rate limiting are not evaluated offline.
* **Selection bias is disclosed in the report**: the generator ranges, rule thresholds and the default cost limit
  were revised twice after looking at aggregate results of earlier runs. The confirmation set (same distribution,
  new samples) matches the test split closely, which rules out sample-specific overfitting but not this.

## Reproducibility

Seeded generator and splits; environment, library versions and hardware are written into the report. The default
dataset is rebuilt only with `--rebuild-dataset` (cached in `ml/data/generated/`, git-ignored). A quick smoke run is
`python -m ml.run --per-category 40 --confirm-seed 0 --no-save-model --skip-bench`, which is what CI executes.
